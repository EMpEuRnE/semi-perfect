# ภารกิจประจำวัน — ส่งมอบ

วันที่ 25 ตุลาคม 2026 · ต่อจากระบบ Brand Campaign/Challenge

## ภารกิจเริ่มต้น

| ภารกิจ | ความยาก | เป้าหมาย | แต้มหลังครบและอนุมัติ |
|---|---|---|---|
| เดิน 3,000 ก้าว | ง่าย | 3,000 steps | 30 |
| ออกกำลังกาย 15 นาที | ปานกลาง | 15 minutes | 50 |
| เดินหรือวิ่ง 2 กิโลเมตร | ปานกลาง | 2 km | 60 |

ทั้งสามรายการเป็น daily และต้องมีหลักฐาน URL หรือบันทึกรายละเอียดที่ระบุกิจกรรม ผล และวันที่ ผู้ดูแลตรวจเองใน /admin ไม่ใช้ Health API และไม่อ้างว่าตรวจภาพ/กิจกรรมจริงอัตโนมัติ ขั้นนี้ยังไม่มีอัปโหลดไฟล์ภาพ

ออกกำลังกาย 15 นาทีเลือกเดิน วิ่ง ปั่นจักรยาน ว่ายน้ำ หรือกิจกรรมอื่นได้ ส่วน 2 กิโลเมตรเลือกเดินหรือวิ่งได้ ทั้งชนิดกิจกรรมและหน่วยตรวจซ้ำที่ backend

## กติกาของรอบวัน

- Backend คำนวณวันจาก `now() at time zone 'Asia/Bangkok'` ไม่รับวันที่รอบจาก client
- หนึ่งบัญชีเริ่มได้หนึ่ง participation ต่อ Mission ต่อวัน Unique index บังคับ `(user_id, mission_id, participation_date)`
- หนึ่งรอบได้รับแต้มเมื่อ approved progress ครบเป้าหมายเท่านั้น อนุมัติบางส่วนเพิ่ม progress แต่ยังไม่ให้แต้ม
- Ledger มี round ID และ unique index กันเครดิตซ้ำ พร้อม trigger ตรวจเครดิตเดิมที่อ้างผ่าน activity ด้วย
- เรียก Join ซ้ำหรือเริ่มหลังทำสำเร็จในวันเดียวกันจะคืนรอบเดิม ไม่รีเซ็ต progress
- วันใหม่เริ่มรอบใหม่ได้โดยไม่ต้อง cron หรือสร้างสำเนา Mission ทุกวัน
- ส่งผลได้เฉพาะภายในวันของรอบ ถ้าข้ามเที่ยงคืนแล้วต้องเริ่มรอบปัจจุบัน
- ผลที่ส่งทันเวลารอ Admin อนุมัติวันถัดไปได้ แต้มผูกกับวันของรอบเดิม ไม่ถูกย้ายมานับเป็นภารกิจของวันตรวจ
- ดังนั้น Wallet อาจได้รับแต้มจากหลายรอบวันในการตรวจวันเดียว แต่แต่ละ Mission/วันได้รับสูงสุดหนึ่งครั้ง
- ถ้าถูกปฏิเสธ ส่งใหม่ในรอบเดิมได้ก่อนเที่ยงคืน หลังจบรอบส่งเพิ่มไม่ได้
- รอบใหม่เก็บ snapshot เงื่อนไข เป้าหมาย แต้ม และชนิดกิจกรรมตอนเริ่ม เพื่อไม่เปลี่ยนเกณฑ์ของผู้เข้าร่วมย้อนหลัง

## หน้าจอ

- หน้ารวมและรายละเอียดแสดงชื่อ รายละเอียด เงื่อนไข ความยาก เป้าหมาย หน่วย และแต้มเสมอ
- ปุ่มเริ่มวันนี้ / ทำต่อหรือดูผลตรวจ / ดูผลที่อนุมัติแล้ว สอดคล้องกับสถานะ
- Progress bar นับเฉพาะค่าที่อนุมัติ
- ยอด “ส่งทั้งหมด” รวมทุก submission รวมรายการไม่ผ่านและส่งซ้ำ โดยมีคำอธิบายกำกับ จึงอาจเกินเป้าหมายได้
- ยอด “รอตรวจ” แสดงแยกและไม่แสดงเหมือนเป็น progress หรือแต้มที่ได้รับแล้ว
- เลือกประเภทกิจกรรมก่อนส่งสำหรับภารกิจที่รับหลายรูปแบบ
- History แยกแต่ละวันและลิงก์ไป `/missions/<id>?day=YYYY-MM-DD` เพื่อดูรอบเดิม ขณะรายละเอียดปกติเป็นรอบวันนี้
- Admin เห็นวันของรอบและ snapshot เป้าหมาย/แต้มก่อนตัดสินผล แม้เป็นหลักฐานจากวันก่อน
- ข้ามวันใน tab เก่าแล้วส่ง ระบบ backend จะปฏิเสธและให้เริ่มรอบปัจจุบันจากหน้าที่โหลดใหม่

## การเก็บข้อมูลเดิม

- Missions เดิมมี recurrence เริ่มต้นเป็น once จึงยังเป็นภารกิจครั้งเดียวตามพฤติกรรมเดิม
- Participation เดิมเก็บ ID, status, progress, timestamps และ completed_at ไว้ตามเดิม โดย participation_date/snapshot เป็น null
- ไม่ย้ายหรือแก้ไข ledger เก่าเพื่อเติม round ID เพราะ ledger เป็น append-only; trigger ใหม่ตรวจหาการจ่ายซ้ำจาก activity ของรายการเก่าได้ด้วย
- Unique ของภารกิจครั้งเดียวเปลี่ยนเป็น partial index เฉพาะแถววันที่ null ส่วนภารกิจ daily ใช้ unique รายวัน
- Foreign key ของกิจกรรมที่ผูก participation ID เดิมยังอยู่
- ห้ามเปลี่ยน recurrence ของ Mission ที่มีคนเริ่มแล้ว ให้สร้างรายการใหม่แทน
- รอบเก่าที่เริ่มก่อนอัปเกรดไม่มี snapshot และยังใช้เงื่อนไขเดิมจาก Mission ตามระบบก่อนอัปเกรด รอบใหม่เท่านั้นที่เก็บ snapshot
- ปรับเฉพาะ conflict clause ของ local seed เดิมให้เข้ากับ index ใหม่ ไม่ใช่ไฟล์สำหรับรันบนฐานข้อมูลจริง

## Seed ที่รันซ้ำได้

`202610250009_daily_mission_seed.sql` ใช้ seed_key ไม่ซ้ำสามรายการ และ `ON CONFLICT (seed_key) DO NOTHING` ไม่ใส่ auth users ไม่ล้างข้อมูล และไม่ update รายการเดิมเมื่อรันซ้ำ แม้รายการนั้นถูกผู้ดูแลแก้ภายหลัง

ภารกิจเดิม เช่น 5,000 ก้าว ไม่ถูกแทนที่ จึงอาจเห็นมากกว่าสามรายการบนหน้ารวม โดยสามรายการใหม่มีป้ายภารกิจรายวัน

## ติดตั้งบนฐานข้อมูลเดิม

ต้องมี migration ขั้นก่อนหน้าถึง `202610250007_brand_campaign_management.sql` แล้ว จากนั้นรันใน Supabase SQL Editor ตามลำดับ:

1. `supabase/migrations/202610250008_daily_mission_rounds.sql` — เพิ่มรอบวัน, snapshot, การกันแต้มซ้ำ, aggregate view และปรับ RPC
2. `supabase/migrations/202610250009_daily_mission_seed.sql` — เพิ่ม 3 เควส; ไฟล์นี้รันซ้ำได้

ไม่รัน INSTALL_FRESH.sql หรือ seed.sql เดิมกับฐานข้อมูลที่มีข้อมูลอยู่ INSTALL_FRESH.sql อัปเดตไว้สำหรับฐานข้อมูลว่างและรวมสามเควสใหม่แล้ว

Restart เว็บและเปิด /missions ถ้ายังไม่ได้รัน migration อาจพบสถานะโหลดข้อมูลไม่สำเร็จ ต้องติดตั้ง SQL ให้ตรงกับโค้ดก่อน

Migration ไม่ยกระดับบัญชีใดเป็น Admin; การตรวจภารกิจส่วนกลางยังต้องใช้บัญชี Admin ที่เจ้าของโปรเจกต์เตรียมไว้ตามระบบสิทธิ์เดิม

## เปิดโค้ดบน Windows

แตก ZIP แล้วเปิดโฟลเดอร์ `Move-and-earn-daily-missions` ที่มี package.json คัดลอก `.env.local` จากโฟลเดอร์เดิมมาไว้ข้าง package.json

```powershell
npm.cmd exec --yes --package=pnpm@11.25.0 -- pnpm install --frozen-lockfile --node-linker=hoisted
```

```powershell
.\node_modules\.bin\next.cmd dev
```

ใช้ Local URL ที่ Terminal แสดง และเปิด Terminal ค้างไว้ ไม่ต้องใช้ START.cmd เดิม

## ผลตรวจจริง

| ชุดตรวจ | ผล |
|---|---|
| lint / typecheck / production build | ผ่าน |
| Unit/action/data checks | 95 checks ผ่าน (รวม 23 checks สำหรับ timezone/status/การเลือกข้อมูลรายวันและ snapshot) |
| SQL integration | 145 assertions ผ่านใน PGlite พร้อม auth.uid() จำลอง |
| Upgrade compatibility | ผ่าน: เทียบฟิลด์เดิมของ Missions, participations, ledger แล้วเหมือนเดิม และกิจกรรมที่เริ่ม/ส่งก่อนอัปเกรดยังทำต่อจนได้แต้มเดิมได้ |
| HTTP production server | 21 checks ผ่าน แบบไม่ตั้งค่า Supabase |
| Fresh installer | ติดตั้ง schema + 3 เควส และรัน seed ใหม่ซ้ำแล้วยังมี 3 รายการ |

SQL ครอบคลุมขอบวันเวลาไทย, 3 เควสและแต้ม, Join ซ้ำ, หลักฐานบังคับ, ชนิดกิจกรรม, ค่าทศนิยมของก้าว, ผู้ใช้แก้วันเองไม่ได้, progress ที่อนุมัติแยกจากยอดส่ง/รอตรวจ, RLS ของ aggregate, ปฏิเสธแล้วส่งใหม่, partial approval, ได้แต้มครั้งเดียว, เดิน/วิ่ง/ว่ายน้ำตามหน่วย, แยกรอบใหม่, การอนุมัติวันเก่า, snapshot หลังผู้ดูแลเปลี่ยน Mission และ seed ไม่ทับข้อมูล

การจำลองวันก่อนใน SQL test ใช้ privileged fixture ตั้งวันที่รอบเพื่อทดสอบการแบ่งวัน ไม่ได้รอเวลาจริงข้ามวันหรือเปลี่ยน clock ของเครื่อง ส่วนขอบเที่ยงคืนทดสอบฟังก์ชันด้วย timestamps โดยตรง

## ข้อจำกัดที่ยังเหลือ

- ยังไม่ได้รัน SQL หรือทดสอบ flow นี้กับ Supabase จริงในรอบนี้
- ยังไม่ได้ทดสอบหลาย connection พร้อมกันบน PostgreSQL จริง แม้มี unique indexes และ row locks
- ยังไม่ได้ตรวจภาพ desktop/mobile หรือ flow หลังล็อกอินผ่าน browser จริง; Chromium ของ environment ยังไม่พร้อมจากการตรวจรอบก่อน
- การตรวจหลักฐานเป็น manual review ไม่ได้พิสูจน์การออกกำลังกายด้วยอุปกรณ์หรือ AI
- ยังไม่ได้ deploy หรือ push branch ขึ้น GitHub
- ZIP ไม่รวม .env.local, node_modules, .next หรือประวัติ Git

งานนี้เพิ่มเฉพาะ daily missions และส่วนที่จำเป็นต่อรอบวัน ไม่เพิ่มคูปองหรือหน้า Progress รวม
